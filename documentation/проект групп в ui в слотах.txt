Цели и контекст

Дать администраторам возможность объединять преподавателей в именованные группы.

В веб-модуле «Слоты» фильтровать сетку по выбранной группе или показывать всех.

Сейчас группы временно хранятся в LocalStorage на клиенте; документ описывает серверную реализацию, чтобы сделать группы общими и надёжными.

Область функционала

CRUD групп (создание/чтение/изменение/удаление).

Управление составом группы (привязка преподавателей).

Отдача списка групп и членов для быстрой фильтрации на фронте.

Аудит действий администраторов (кто/когда создал/изменил/удалил).

Импорт групп с клиента (однократно, для миграции из LocalStorage).

Не входит в объём (пока)

Иерархия/вложенные группы.

Автосинхронизация с внешними системами.

Роли/права внутри группы.

Модель данных

Минимальные сущности:

teacher_groups

id (uuid)

name (varchar 128, уникально в пределах организации/тенанта)

created_at, updated_at (timestamp)

created_by (user_id)

(опционально) org_id/tenant_id, если мультитенант

teacher_group_members

group_id (fk → teacher_groups.id, on delete cascade)

teacher_id (fk → teachers.id)

added_at (timestamp)

PK: (group_id, teacher_id)
Индексы:

teacher_group_members на (teacher_id) — быстрый поиск «в каких группах учитель».

Уникальный индекс на (org_id, name) — защититься от дублей.

Правила доступа (RBAC)

admin: полный CRUD групп и участников.

teacher/client/guest: доступа нет.

(опционально) viewer: только чтение списка групп с составом.

Все эндпоинты только с аутентификацией; проверка org_id/tenant_id, если есть.

Валидация и бизнес-правила

name: 1–128 символов, обрезка пробелов, запрет дубликатов в рамках организации.

Состав группы — только существующие и активные teacher_id.

Ограничения: до N групп на организацию (например, 200), до M учителей в группе (например, 1000) — значения настраиваемы.

Удаление группы каскадно удаляет участника (ON DELETE CASCADE).

При переименовании — конфликт имён = 409.

API (черновая спецификация)

Все пути предполагают префикс /admin, JSON, время в ISO-8601, ошибки в едином формате {error, code, detail}.

GET /teacher-groups

Параметры: include_members=bool (по умолчанию false)

Ответ: массив групп; при include_members=true внутри каждой группы teacher_ids: number[].

POST /teacher-groups

Тело: { name: string }

Ответ: созданная группа.

GET /teacher-groups/{id}

Ответ: группа + teacher_ids.

PATCH /teacher-groups/{id}

Тело: { name?: string }

Ответ: группа обновлена.

PUT /teacher-groups/{id}/members

Тело: { teacher_ids: number[] } — атомарная замена состава.

Ответ: { group_id, teacher_ids }.

PATCH /teacher-groups/{id}/members (опция для частичных операций)

Тело: { add?: number[], remove?: number[] }.

Ответ: актуальный состав.

DELETE /teacher-groups/{id}

Ответ: 204 No Content.

POST /teacher-groups/import (миграция с клиента)

Тело: { groups: {name: string, teacher_ids: number[]}[] }

Поведение: создаёт отсутствующие, для совпавших по имени — предлагает стратегию merge|skip|replace через параметр strategy (по умолчанию merge).

Ответ: отчёт: { created: n, merged: n, skipped: n, replaced: n }.

Техдетали:

ETag/If-None-Match или Last-Modified для листинга — чтобы фронт мог кэшировать.

Пагинация пока не нужна (объём мал), но резервируем ?limit/offset.

Коды ошибок (единый подход)

400 — неверные данные (name пустой, лишние поля, невалидные teacher_id).

401/403 — аутентификация/авторизация.

404 — группа/учитель не найдены.

409 — конфликт имени группы, конфликт стратегии import.

422 — частичная операция (например, add содержит несуществующие teacher_id) — вернуть список проблемных ID.

Аудит и наблюдаемость

Журнал аудита: action (create|update|delete|set_members|import), actor_id, group_id, diff (до/после), ts.

Метрики: количество групп на организацию, средний размер группы, частота фильтраций (через фронтовую телеметрию).

Логи — структуированные, с корреляцией запроса.

Производительность и кэширование

Состав группы хранится в teacher_group_members; для быстрых ответов GET /teacher-groups?include_members=true допускается материализованный JSON-массива teacher_ids в представлении/кеш-поле (teacher_groups.members_cache) с обновлением при изменениях (опционально).

ETag/304 для листинга групп.

Индексы описаны выше.

Безопасность

Все операции — только по HTTPS.

Проверка принадлежности teacher_id текущему org_id.

Защита от «массовых» списков в PUT members: лимит длины массива и общая проверка нагрузки.

Rate-limit базовый (например, 60 rps / токен на групповые операции).

Тест-план (минимум)

CRUD: создание, переименование, удаление; повтор имени → 409.

Состав: полная замена, add/remove; id не существует → 422 с перечислением.

Границы: пустой список, 1 учитель, много учителей; лимиты.

Авторизация: доступ только admin; отрицательные проверки.

Импорт: merge|skip|replace, конфликты по имени, отчёт.

Конкурентность: два одновременных PATCH/PUT → корректная последняя версия (ETag или транзакции).

План миграции с LocalStorage

Добавить в UI кнопку «Синхронизировать группы» (видна админам).

Клиент читает LocalStorage (teacher_groups_v1) и шлёт на POST /teacher-groups/import?strategy=merge.

После успешного импорта — предлагает «удалить локальные группы» (или оставить как локальный кеш).

Переключить фронт на чтение групп с бэка; LocalStorage использовать как offline-кеш (TTL) при 5xx.

Развёртывание и поэтапный ввод

Катить миграцию БД.

Включить эндпоинты за фичефлагом.

Включить UI-кнопку «Синхронизировать» только на стейдже; проверить конечные сценарии.

Перевести прод фронт на серверные группы; оставить fallback на LocalStorage на 1–2 релиза.

Включить аудит и мониторинг.

Риски и как их снижаем

Дубли имён при импорте → стратегия и 409 с дружественным сообщением.

Большие группы → лимиты и индексы.

Мультитенант → строгая проверка org_id везде, уникальность имён в рамках тенанта.

Случайное удаление → подтверждение на фронте + аудит.
